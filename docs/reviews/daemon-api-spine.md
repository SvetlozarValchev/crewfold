## Failure proof

- Injected failures: attempt to start a second daemon against a live socket;
  attempt to start with a live data-directory lock; kill the owned daemon without
  cleanup to leave a stale socket; hold a partial request open during shutdown;
  and place a regular file or lock symlink at a protected path.
- Injection seam/barrier: real-process startup in the black-box scenario and
  deterministic listener/connection barriers in daemon component tests.
- Expected diagnosis and recovery: live socket and data-directory conflicts have
  different stable error codes; stale sockets are recovered only after identity
  and type rechecks; unrelated files and symlink targets remain untouched; open
  partial reads cannot prevent shutdown.
- Observed diagnosis and recovery: `socket_in_use` and `data_dir_in_use` were
  reported as expected, the same socket path was reclaimed after the crash, the
  restarted daemon stopped cleanly, protected paths were preserved, and the
  in-flight read test completed within its deadline.
- Operation/event IDs: request IDs are generated by the client, returned by the
  API, and present in structured request logs. M1 has no durable event journal.

## Persistence and recovery

- Durable state introduced or changed: no domain state. The daemon creates only
  an owner-only `daemon.lock` coordination file in the selected data directory.
- Restart/crash points tested: forced process death after readiness leaves the
  socket pathname behind; the daemon is then restarted with the same data and
  socket paths.
- Reconciliation outcome: the dead socket is distinguished from a reachable live
  daemon, revalidated, removed, rebound, and removed again on graceful shutdown.
- Migration fixture added: N/A; SQLite and migrations begin in M2.
- Backup/restore impact: none; the lock file is not application data.

## Security and autonomy

- New actions/capabilities: bind a local Unix socket, accept bounded JSON
  request/response messages, report process health, and stop the owning daemon.
- Allowed/denied scope: only an explicit socket and data directory are used;
  socket collisions, live locks, non-socket paths, and symlink lock paths are
  denied. There is no project, repository, provider, or network action.
- Secret/redaction impact: logs contain request ID, method, status, and duration;
  request bodies are not logged. The protocol carries no credentials in M1.
- External side effects: local directory, lock-file, and socket creation only.
- Human approval boundary: the local operator explicitly starts and stops the
  foreground process.

Newly created data directories use mode `0700`; socket and lock files use mode
`0600`. Lock opening rejects symlinks, and socket cleanup removes a path only when
it still identifies the socket created by this process.

## Compatibility

- API/schema changes: introduced newline-delimited local API protocol version 1,
  request/response envelopes, protocol negotiation, `system.status`, and
  `system.stop`, with stable schema URNs and structured error codes.
- Adapter/runtime compatibility changes: none; no runtime or provider adapter is
  implemented.
- Earlier milestone scenarios rerun: M0 passes unchanged as part of every check.
- Upgrade/rollback impact: no persistent domain state exists. An M1 client fails
  explicitly when its supported protocol range does not overlap the daemon's.

## Known limitations and deferrals

- The daemon is foreground-only and requires explicit data-directory and socket
  paths; there is no background service installation or automatic discovery.
- Transport support is Unix-only. Authentication is the operating-system user's
  access to the owner-only socket; there is no multi-user or remote transport.
- One request is handled per connection. Subscriptions, events, streaming,
  request idempotency, and durable command recovery are not implemented.
- SQLite, workspace state, an event journal, and migrations are deferred to M2.
- Projects, agents, tasks, runtimes, MCP, Herdr, and providers remain deferred to
  their roadmap milestones.
