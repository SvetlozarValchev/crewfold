Proposal · 05 November 2026

A board the room can choose to use

Tasks describe the work. Questions collect decisions. Neither controls the sessions.

Add a Board view to each room, beside its conversation. Documents remain shared knowledge; cards link to them instead of becoming another documentation system. An unused board is simply empty. Joining, chatting, sharing documents, and doing work never require a task.

The owner or any participant can guide the room to maintain the board through normal conversation. Crewfold does not automatically turn messages into tasks, enforce that guidance, schedule agents, or start sessions.

1. Small shared records

Only a title is required. A task defaults to Backlog; a question defaults to Open. Creator and editor attribution are history, not ownership. All authorized room humans and joined agents can create, edit, archive/restore tasks, answer questions, and resolve/reopen them. Leaving does not delete records or reassign work; listed departed participants get a “left” indication.

2. The web and CLI are the same surface

Cards open an editor; drag-and-drop is a shortcut for changing status. Participant filters answer “who is working on what.” Questions stay next to the board, including requests awaiting human input. An answer is published to the room once, attributed to its author, and linked back to the question. “Answer & resolve” is optional; anyone may reopen it later.

Document links display a filename and publisher, not opaque IDs. Links can follow the latest logical revision; evidence links can pin a revision. The prototype's sample document buttons only preview illustrative contents.

3. CLI proposal — not implemented commands

Keep the existing room namespace and actor authentication. Local agents use crewfold; remote agents use crewfold-connector with the same arguments. Short titles are arguments; longer notes and answers accept stdin. No new provider-specific setup.

crewfold room task list release-room
crewfold room task create release-room "Check reconnect behavior"
crewfold room task show release-room T-12 --json
crewfold room task update release-room T-12 --status in-progress --add-worker @atlas
crewfold room task update release-room T-12 --blocked "Waiting for a fixture"
crewfold room task update release-room T-12 --clear-blocked --status done
crewfold room task archive release-room T-12
crewfold room task restore release-room T-12

crewfold room question list release-room --open
crewfold room question ask release-room "Ship without offline mode?" --human-input
crewfold room question answer release-room Q-3 --stdin <<'ANSWER'
Ship this release online-only. Keep offline mode in the backlog.
ANSWER
crewfold room question resolve release-room Q-3
crewfold room question reopen release-room Q-3

update --stdin replaces task notes; --add-worker/--remove-worker change the descriptive participant list; --link-document adds an existing document reference. Answers support --resolve to combine the two actions. All mutations return the record ID and revision so success is explicit. No automatic assignment or status changes from a participant's runtime state.

4. Notification behavior — useful, not a second chat flood

ActionRoom behavior
Create / edit / move / archive a taskUpdate board and task history. No automatic chat post or agent wake. Publish a normal room message when coordination is needed.
Raise a questionOne attributed question event in the room, linked to Q-ID. Use ordinary room delivery batching. A human-input hint highlights it in the UI; it does not summon a runtime.
Answer a question (web or CLI)One canonical answer event appears in the room and question thread. Notify joined participants through existing delivery, exclude the author, and batch normally. Explicit mentions follow existing mention handling.
Resolve / reopenOne small linked room event. Answer-and-resolve is a single event, not two notifications. No generated acknowledgement or summary.

Question answers remain ordinary room collaboration, not privileged owner instructions. The event preserves whether the author is a human or agent. Multiple answers remain visible; the latest answer does not overwrite earlier replies. No answer automatically makes a task Done.

5. Fit the existing implementation

The current app already shares an SQLite store and RPC layer between the local CLI, browser, and restricted tailnet API. Extend that path instead of adding a service or duplicating state in Markdown files. Existing product documentation explicitly excludes task tracking; update that boundary to permit shared records while continuing to exclude work execution.

  • Storage: room-local task/question numbers backed by internal IDs; record version; actor IDs; timestamps. Tables for tasks, task participants, questions, and change history. Question answers reference canonical room events instead of copying message bodies.
  • Correctness: update a record and its audit/event entry in one transaction. Expected-version checks prevent silent overwrites, not concurrent participation. On conflict return current state so the caller can merge. Use client operation IDs to deduplicate retried creates and answers.
  • Access: use existing room/device membership checks for every RPC, including referenced participants and documents. No creator-only permissions or special steward authority. Keep humans and agent identities distinct; never use directories as task identity.
  • History: archive tasks without deleting their IDs or links; explicit restore brings them back. Resolved questions have their own filter and can be reopened. Done and resolved do not mean verified or human-approved.
  • Performance: paginated task lists and question history; bounded recent Done cards with “Load more.” Fetch details only when opened. Do not add every task or full history to room snapshots or agent prompts.
  • Delivery: question events use the existing sequence/cursor, batching, self-exclusion, and connector transport. Task-only changes are readable via task APIs and UI refresh, without entering the notification stream.

6. What this prototype demonstrates

Create and edit cards; move them by drag-and-drop or status select; list multiple workers; filter/search; archive/restore; raise questions; answer as a human or agent; optionally resolve; reopen; see answers in Conversation; preview linked documents. Switch “Preview as” to prove editing is not creator-locked.

Everything is in memory and resets on reload. No network calls, actual CLI, database, delivery, authentication, concurrent editors, Markdown renderer, or persistent storage are implemented here. The mock displays notes and answers as plain text. The real UI should reuse its existing Markdown renderer.

7. First implementation slice

  1. Store + shared RPC + CLI/connector commands, with tests for room scoping, shared edits, version conflicts, deduplicated answers, and departed participants.
  2. Board + question section + existing room-feed rendering, document references, and filters. Include keyboard editing, pagination, and archive/restore.
  3. Exercise with one room and two existing sessions: different creators/editors, an agent answering a human-input question, simultaneous answers, and batched delivery. No rejoin or runtime restart should be required merely to use records.

Leave out sprints, estimates, priorities, deadlines, custom workflow builders, dependency graphs, subtasks, auto-assignment, agent schedulers, review gates, and Git integrations. Consider them only after a room actually needs them.

Research and design choices

GitHub Projects’ board layout treats columns as a view over a field, and dragging changes that field. That is the useful interaction to borrow here—not its larger project machinery.

Linear’s assignment model uses one assignee and distinguishes agent delegation from human ownership. Crewfold needs a different convention: optional participants working on a record, without assignment-based authority or delegated execution. The questions section is our proposed room-native design, not a claim about either product.

Recommendation: ship tasks and questions as two lightweight, freely editable room records. Preserve the distinction between recording a decision, discussing it, and commanding an agent.
